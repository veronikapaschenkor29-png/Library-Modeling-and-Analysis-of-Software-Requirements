# 0004. Штраф за прострочення як окрема сутність FINE

- **Status:** прийнято
- **Date:** 2026-11-16

## Контекст та постановка проблеми

При простроченні повернення книги нараховується штраф. Потрібно вирішити, як моделювати штрафи: як атрибут LOAN або як окрему сутність.

## Розглянуті варіанти

1. **Штраф як атрибут LOAN** (fine_amount, fine_paid).
   - Переваги: простий запит, один JOIN.
   - Недоліки: якщо штрафів кілька (наприклад, за різні періоди), потрібно додавати поля; порушення 3NF при кількох штрафах.

2. **Окрема сутність FINE**, пов'язана з LOAN відношенням 1 : 0..1.
   - Переваги: 3NF, можливість кількох штрафів на один LOAN, відстеження статусу оплати.
   - Недоліки: додатковий JOIN.

## Рішення

Обрано **Варіант 2** - окрема сутність FINE.

### Позитивні наслідки

- **3NF:** Штраф ізольований в окремій таблиці, LOAN не містить фінансових атрибутів.
- **Кілька штрафів:** Один LOAN може мати кілька FINE (наприклад, за різні періоди прострочення).
- **Статус оплати:** Поле status (unpaid/paid/waived) відстежує стан штрафу.
- **Аудит:** Зберігається історія нарахувань та оплат.

### Негативні наслідки

- Додатковий JOIN при запитах на штрафи читача.
- Потребує індексу на fine.loan_id для продуктивності.

## Пов'язані рішення

- ADR 0001: Виділення BOOK_COPY (LOAN прив'язаний до BOOK_COPY).
- ADR 0006: Штраф як extend на повернення (FINE створюється при поверненні простроченої книги).
