# 0009. Модульний моноліт з API Gateway, адаптерами та Outbox

- **Status:** прийнято
- **Date:** 2026-11-18

## Контекст та постановка проблеми

Система бібліотеки повинна підтримувати інтеграцію з зовнішніми системами (email, платіжний шлюз для штрафів). Потрібно вирішити архітектурний стиль та спосіб інтеграції.

## Розглянуті варіанти

1. **Мікросервіси** (окремі сервіси для кожного модуля).
   - Переваги: незалежне масштабування, ізоляція.
   - Недоліки: складність розгортання, мережеві затримки, складніше тестувати.

2. **Модульний моноліт** з чіткими межами модулів.
   - Переваги: простота розгортання, транзакційна цілісність, легше тестувати.
   - Недоліки: складніше масштабувати окремі модулі.

3. **Модульний моноліт + API Gateway + адаптери + Outbox**.
   - Переваги: ізоляція зовнішніх систем, надійна доставка повідомлень, чистота доменної логіки.
   - Недоліки: додаткова складність.

### Позитивні наслідки

- **Модульність:** Чіткі межі між модулями (Catalog, Member, Loan, Fine, Notification).
- **Ізоляція зовнішніх систем:** Адаптери ізолюють доменну логіку від зовнішніх API (email, платіжний шлюз).
- **Надійність:** Outbox-патерн забезпечує надійну доставку повідомлень (email, SMS).
- **Транзакційна цілісність:** Один процес, одна база даних - ACID-гарантії.

### Негативні наслідки

- Складніше масштабувати окремі модулі (але для бібліотеки це не критично).
- Додаткова складність Outbox-патерну.

## Пов'язані рішення

- ADR 0001-0008: Усі попередні рішення в рамках модульного моноліту.
