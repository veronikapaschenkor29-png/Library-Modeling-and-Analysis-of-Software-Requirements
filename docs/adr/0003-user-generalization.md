# 0003. Узагальнення USER для ролей MEMBER та LIBRARIAN

- **Status:** прийнято
- **Date:** 2026-11-16

## Контекст та постановка проблеми

У бібліотеці є два типи користувачів: читачі (MEMBER) та бібліотекарі (LIBRARIAN). Обидва мають спільні атрибути (email, password, full_name), але також специфічні (номер читацького квитка vs табельний номер). Потрібно вирішити, як моделювати цю ієрархію.

## Розглянуті варіанти

1. **Одна таблиця USER з полем role** (MEMBER/LIBRARIAN).
   - Переваги: простий запит, один JOIN.
   - Недоліки: NULL-поля для специфічних атрибутів, порушення 3NF, складно додавати нові ролі.

2. **Узагальнення: USER → MEMBER/LIBRARIAN** (table-per-subtype).
   - Переваги: 3NF, чистота схеми, кожна роль має власні атрибути без NULL.
   - Недоліки: додатковий JOIN при запитах.

3. **Узагальнення: USER → MEMBER/LIBRARIAN** (single table inheritance).
   - Переваги: простий запит, один JOIN.
   - Недоліки: багато NULL-полів, порушення 3NF при додаванні нових ролей.

## Рішення

Обрано **Варіант 2** - узагальнення USER → MEMBER/LIBRARIAN (table-per-subtype).

### Позитивні наслідки

- **3NF:** Кожна роль має власну таблицю зі специфічними атрибутами, спільні атрибути в USER.
- **Розширюваність:** Легко додати нову роль (наприклад, ADMIN) без зміни існуючих таблиць.
- **Цілісність:** FK від MEMBER/LIBRARIAN до USER забезпечує, що кожна роль прив'язана до існуючого користувача.
- **Безпека:** Роль визначається наявністю запису в MEMBER або LIBRARIAN, а не полем role.

### Негативні наслідки

- Додатковий JOIN при запитах на дані користувача з його роллю.
- Потребує перевірки, що користувач має хоча б одну роль (або жодної - для анонімних).

## Пов'язані рішення

- ADR 0001: Виділення BOOK_COPY (USER - центральна сутність для акторів).
- ADR 0009: Модульний моноліт (USER-модуль ізолює автентифікацію).
