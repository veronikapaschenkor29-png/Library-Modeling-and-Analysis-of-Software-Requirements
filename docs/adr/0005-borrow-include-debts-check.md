# 0005. Перевірка боргів при видачі книги (include)

- **Status:** прийнято
- **Date:** 2026-11-17

## Контекст та постановка проблеми

При видачі книги системі необхідно перевірити, чи має читач прострочені борги (штрафи). Якщо має — видача заборонена. Потрібно вирішити, як моделювати цю перевірку: як частину use case Borrow, чи як окремий use case.

## Розглянуті варіанти

1. **Окремий use case CheckDebts**, який викликається перед Borrow.
   - Переваги: модульність, повторне використання.
   - Недоліки: додатковий крок для користувача, складніша логіка.

2. **Include-зв'язок: Borrow include CheckDebts** — перевірка є частиною Borrow.
   - Переваги: інкапсуляція, читач не бачить окремого кроку.
   - Недоліки: складніше тестувати ізольовано.

## Рішення

Обрано **Варіант 2** — include-зв'язок Borrow include CheckDebts.

### Позитивні наслідки

- **Інкапсуляція:** Читач не бачить окремого кроку перевірки боргів.
- **EARS:** Вимога EARS-03 (перевірка боргів) реалізована як частина UC_Borrow.
- **Трасування:** Легко простежити зв'язок UC_Borrow → EARS-03 → CheckDebts.

### Негативні наслідки

- Складніше тестувати перевірку боргів ізольовано від видачі.

## Пов'язані рішення

- ADR 0006: Штраф як extend на повернення (FINE створюється при поверненні).
- ADR 0007: Послідовність на сценарій (S1 — видача книги включає перевірку боргів).
