# 0006. Штраф як extend-зв'язок на повернення книги

- **Status:** прийнято
- **Date:** 2026-11-17

## Контекст та постановка проблеми

При поверненні книги, якщо вона прострочена, нараховується штраф. Потрібно вирішити, як моделювати цей процес: як частину use case Return, чи як окремий use case.

## Розглянуті варіанти

1. **Окремий use case CreateFine**, який викликається після Return.
   - Переваги: модульність.
   - Недоліки: додатковий крок, складніша логіка для користувача.

2. **Extend-зв'язок: Return extend CreateFine** - штраф нараховується автоматично при поверненні простроченої книги.
   - Переваги: інкапсуляція, автоматичне нарахування.
   - Недоліки: складніше тестувати ізольовано.

## Рішення

Обрано **Варіант 2** - extend-зв'язок Return extend CreateFine.

### Позитивні наслідки

- **Інкапсуляція:** Читач не бачить окремого кроку нарахування штрафу.
- **Автоматизація:** Штраф нараховується автоматично при поверненні простроченої книги.
- **EARS:** Вимога EARS-06 (штраф за прострочення) реалізована як частина UC_Return.

### Негативні наслідки

- Складніше тестувати нарахування штрафу ізольовано від повернення.

## Пов'язані рішення

- ADR 0004: Штраф як окрема сутність FINE.
- ADR 0007: Послідовність на сценарій (S2 - повернення книги включає нарахування штрафу).
