# 0006. Уточнення ADR 0004: створення `FINE` при поверненні простроченої видачі (внутрішня дія `UC_Return`)

* Статус: прийнято
* Дата: 2026-11-18
* Оновлено: створення FINE - вимога EARS-06 (внутрішня дія UC_Return), не прецедент на діаграмі; див. task-2/spec.md, task-2/DEFENSE.md
* Контекст: Завдання 2 (`task-2/`), уточнення `docs/adr/0004-fine-on-overdue.md`

## Context and Problem Statement

ADR 0004 вже визначив, що `FINE` створюється лише при поверненні простроченої видачі. Цей ADR не змінює того рішення, а уточнює його місце в Use Case моделі: створення `FINE` відбувається при поверненні простроченої видачі в межах `UC_Return` (EARS-06) і не є окремим прецедентом на діаграмі. Формулювання «`Створити штраф` є `<<extend>>` від `UC_Return` як прецедент» скасовано.

## Decision Drivers

* Уникнення дублювання рішення ADR 0004.
* Умовність створення `FINE` в межах `UC_Return` (EARS-06), без окремого прецеденту на діаграмі.
* Трасування до EARS-06.
* Ідемпотентність: один `FINE` на одну прострочену `LOAN`.

## Considered Options

* **Варіант 1:** створювати `FINE` завжди при поверненні (без умови).
* **Варіант 2:** створювати `FINE` як `<<extend>>`-прецедент від `UC_Return` (відхилено для поточної діаграми - внутрішня дія, не потреба актора).
* **Варіант 3:** окремий `UC_CreateFine` / «Обробити прострочення» (відхилено для поточної діаграми - внутрішня дія, методика 6.2.9).
* **Варіант 4 (обрано):** створення `FINE` в межах `UC_Return` при простроченні (EARS-06), без окремого прецеденту на діаграмі.

## Decision Outcome

Обрано **Варіант 4**, узгоджено з ADR 0004. `FINE` створюється при поверненні простроченої видачі в межах `UC_Return` (EARS-06), лише якщо `returned_at > due_at`. Штраф прив'язаний до `LOAN` (ADR 0004), створюється один раз, не дублюється при повторних викликах повернення. Окремого прецеденту на діаграмі немає.

### Consequences

* Good: `UC_Return` охоплює повернення і умовне створення `FINE` без зайвого прецеденту.
* Good: не створюються зайві `FINE` при вчасному поверненні.
* Good: узгоджено з EARS-06 і сценаріями повернення.
* Bad: потрібна перевірка `due_at` vs `returned_at` у `Loan Service`.
* Bad: повторне повернення тієї самої видачі має бути ідемпотентним (перевірка статусу `LOAN`).
