# Завдання 4: Бізнес-процес (діаграма діяльності)

Мета: описати UC_Borrow як єдиний бізнес-процес з усіма сценаріями Gherkin на одній діаграмі діяльності.

## Артефакти

- [spec.md](spec.md) - специфікація завдання 4 (процес, кроки, ролі, розгалуження, повідомлення, трасування).
- [activity.puml](activity.puml) - діаграма зі смугами, розгалуженнями, паралельними перевірками, повідомленнями.
- [activity.md](activity.md) - ті самі блоки в markdown.
- [DEFENSE.md](DEFENSE.md) - захист (§1-§4).

## Вхідні дані

Процес UC_Borrow (видача книги), обраний у Завданні 2; сценарії S1-S5 з task-2/scenarios.feature; учасники і сутності ER з Завдань 1 і 3 (у відповідних гілках).

## Як переглянути

Відкрити activity.puml у PlantUML або activity.md у markdown-рендері з підтримкою plantuml.

## Сценарії і шляхи

| Сценарій | Шлях (коротко) |
| :--- | :--- |
| S1 Успішна видача | борги (ні) → ліміт (<5) → примірник (так) → створити LOAN → кінець |
| S2 Бронювання | борги (ні) → ліміт (<5) → примірник (ні) → створити RESERVATION → кінець |
| S3 Відмова через борги | борги (так) → відмовити → кінець |
| S4 Відмова через ліміт | борги (ні) → ліміт (≥5) → відмовити → кінець |
| S5 Блокування примірника | борги (ні) → ліміт (<5) → примірник (ні, статус «на руках») → відмовити → кінець |

Деталі: spec.md §8.

## Критерії

- Одна форма (діаграма діяльності), декларативний опис.
- ≥1 розгалуження з вичерпними умовами.
- ≥1 паралельна гілка (перевірки боргів і примірника).
- ≥1 повідомлення з показаною реакцією («Пропонується бронювання»).
- Кожен сценарій Gherkin = шлях.
- Смуги ⊆ учасники послідовності (Читач, Система, Бібліотекар).
- Вузли даних ⊆ сутності ER (MEMBER, LIBRARIAN, BOOK_COPY, LOAN, RESERVATION).

Заборонено: символ «-» (лише «-»), STORE, PRODUCT, ORDER, REVIEW, CATEGORY, Seller, Customer, Anonymous, BOOK_GENRE.
