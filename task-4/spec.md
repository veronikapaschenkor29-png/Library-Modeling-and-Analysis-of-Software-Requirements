# Специфікація: Бізнес-процес видачі книги (Завдання 4)

## 1. Намір

Описати процес видачі книги (UC_Borrow) як єдиний бізнес-процес з усіма сценаріями Gherkin (S1-S5) на одній діаграмі діяльності. Посилання: UC Borrow (видача книги), обраний у Завданні 2; сценарії S1-S5 з task-2/scenarios.feature; учасники і сутності ER з Завдань 1 і 3 (у відповідних гілках).

## 2. Обраний процес і форма

Процес = UC_Borrow. Форма = діаграма діяльності (PlantUML activity). Причина вибору: процес має розгалуження (борги, ліміт, наявність примірника) і паралельні перевірки (борги і примірник); запитання «що треба зробити і хто» → діаграма діяльності (методика 9.10). Машина станів не обрана, бо об'єкт LOAN не має станів переходів у межах процесу. BPMN не обрано, бо процес всередині системи, а не між пулами.

## 3. Ролі (смуги)

| Смуга | Учасник | Сутність/роль ER |
| :--- | :--- | :--- |
| Читач | MEMBER (через USER) | MEMBER |
| Бібліотекар | LIBRARIAN (через USER) | LIBRARIAN |
| Система | сервіс видачі + BOOK_COPY, LOAN, RESERVATION | сервіс видачі (не сутність ER), BOOK_COPY, LOAN, RESERVATION |

Учасники ⊆ учасники діаграм послідовності (Завдання 3).

## 4. Кроки процесу (дієслова, не стани)

- Запитати видачу.
- Перевірити борги.
- Перевірити примірник.
- Перевірити ліміт.
- Створити LOAN.
- Встановити статус на руках.
- Створити RESERVATION.
- Надіслати повідомлення читачеві.
- Очікувати відповідь.
- Відмовити.

Кожна дія - одне речення.

## 5. Розгалуження (умови вичерпні)

| Розгалуження | Умова A | Умова B | Сценарій |
| :--- | :--- | :--- | :--- |
| Борги | є прострочені → відмова (S3) | немає → перевірка ліміту | S3 |
| Ліміт | ≥5 активних → відмова (S4) | <5 → перевірка примірника | S4 |
| Примірник | доступний → створити LOAN (S1) | недоступний → бронювання (S2) або блокування (S5) | S1, S2, S5 |

## 6. Паралельна гілка

Fork: паралельно перевіряти борги (LOAN) і примірник (BOOK_COPY). Join: обидві перевірки завершені → перехід до розгалуження.

## 7. Повідомлення

| Відправник | Одержувач | Повідомлення | Реакція |
| :--- | :--- | :--- | :--- |
| Система | Читач | «Пропонується бронювання» | Читач підтверджує або відмовляється |
| Система | Читач | «Відмова: є прострочені борги» | Читач отримує повідомлення, видача не створюється |
| Система | Читач | «Відмова: перевищено ліміт 5 книг» | Читач отримує повідомлення, видача не створюється |
| Система | Читач | «Примірник недоступний, пропонується бронювання» | Читач підтверджує або відмовляється від бронювання |

## 8. Трасування «сценарій → шлях»

| Сценарій Gherkin (Завдання 2) | Шлях на діаграмі (від початку до кінця) |
| :--- | :--- |
| S1 Успішна видача | Початок → перевірка боргів (немає) → перевірка ліміту (<5) → примірник доступний → створити LOAN → встановити статус «на руках» → кінець |
| S2 Книги немає → бронювання | Початок → перевірка боргів (немає) → перевірка ліміту (<5) → примірник недоступний → створити RESERVATION → кінець |
| S3 Борги → відмова | Початок → перевірка боргів (є прострочені) → відмовити → кінець |
| S4 Ліміт → відмова | Початок → перевірка боргів (немає) → перевірка ліміту (≥5) → відмовити → кінець |
| S5 Примірник на руках блокується | Початок → перевірка боргів (немає) → перевірка ліміту (<5) → примірник недоступний (статус «на руках») → відмовити (блокування) → кінець |

## 9. Вузли даних ⊆ сутності ER

MEMBER, LIBRARIAN, BOOK_COPY, LOAN, RESERVATION (з сутностей ER, Завдання 1). FINE не бере участі (створюється при Return).

## 10. Критерії прийняття

- Одна форма (activity), декларативний опис.
- ≥1 розгалуження з вичерпними умовами.
- ≥1 паралельна гілка.
- ≥1 повідомлення з показаною реакцією.
- Кожен сценарій Gherkin = шлях.
- Lanes ⊆ учасники sequence.
- Вузли даних ⊆ сутності ER.

## 11. Поза обсягом

Повернення, оплата штрафу, пошук, фільтрація, автентифікація, технічні деталі транспорту, транзакції БД (як у Завданні 3 §5, але для процесу).
