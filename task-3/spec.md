# Специфікація: Взаємодія (Завдання 3)

## 1. Намір

Описати, що відбувається всередині системи у кожному з п'яти сценаріїв UC_Borrow (Позичення книги), обраного в Завданні 2. Один UC, п'ять сценаріїв. Діаграми послідовності (sequence.puml, S1..S5) показують взаємодію акторів, сервісу видачі та сутностей ER-моделі; технічні деталі транспорту і збереження не показано.

## 2. Обраний UC

UC_Borrow (Позичення книги). Актор: Читач (Reader). Бібліотекар (Librarian) підтверджує наявність примірника. Посилання: task-2/spec.md (розд. 5, 6, 8), task-2/usecase.puml (task-2/usecase.puml: UC_Borrow; Reserve розширює Borrow через extend). Сценарії взято з task-2/scenarios.feature (Gherkin).

## 3. Учасники і відповідність ER

| Учасник на діаграмі | Тип | Сутність ER (task-1) або роль |
| :--- | :--- | :--- |
| Читач | Актор | MEMBER (через USER) |
| Бібліотекар | Актор | LIBRARIAN (через USER) |
| Сервіс видачі | Сервіс (контролер логіки) | не сутність ER; координує видачу |
| Примірник (BOOK_COPY) | Сутність | BOOK_COPY |
| Видача (LOAN) | Сутність | LOAN |
| Бронювання (RESERVATION) | Сутність | RESERVATION |
| Читач 2 | Актор | MEMBER (через USER) |

FINE не є учасником цієї взаємодії, бо створюється при поверненні (EARS-06, ADR 0004).

## 5. Поза обсягом

- Повернення книги: не показано, бо це окремий UC Return з власною взаємодією (EARS-06, ADR 0006); тут розглядається лише позичення.
- Оплата штрафу: не показано, бо створення FINE є результатом повернення, а оплата відбувається пізніше через зовнішній шлюз.
- Пошук і фільтрація: не показано, бо передують запиту видачі і не впливають на логіку Borrow.
- Автентифікація: не показано, бо вважається виконаною до початку сценарію; учасники вже ідентифіковані.
- Технічні деталі транспорту (HTTP, черги): не показано, бо діаграми описують бізнес-взаємодію, а не протоколи.
- Транзакції БД: не показано, бо атомарність збереження прихована за сервісом видачі.

## 6. Критерії прийняття

- Кожен сценарій з Завдання 2 має власну діаграму.
- Учасники відповідають ER-моделі (Завдання 1).
- Є щонайменше один alt у кожній діаграмі.
- Activation bars починаються до умовного фрагмента і закінчуються після нього.
- Назви викликів реалістичні (запит видачі, перевірити статус, створити видачу).
