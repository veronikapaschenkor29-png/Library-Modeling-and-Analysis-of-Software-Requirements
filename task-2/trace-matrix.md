## 3. Передумови та постумови ключових UC

### UC_Borrow (Позичити книгу)
- **Preconditions:** Читач ідентифікований як `MEMBER`; немає прострочених боргів (EARS-02); активних позик < 5 (EARS-03); існує доступний `BOOK_COPY` або пропонується бронювання (EARS-04).
- **Postconditions:** створено `LOAN` з `due_at` = `issued_at` + 14 днів (EARS-01); `BOOK_COPY.status` → «на руках»; за відсутності примірника створюється `RESERVATION` (EARS-04); примірник блокується для інших (EARS-05).

### UC_Return (Повернути книгу)
- **Preconditions:** існує `LOAN` для примірника; повернення ініціює `Reader` або `Librarian`.
- **Postconditions:** оновлено `LOAN` (`returned_at`, статус); `BOOK_COPY.status` → «доступний»; якщо прострочено — створено `FINE` (EARS-06, ADR 0004/0006).

### UC_Reserve (Забронювати книгу)
- **Preconditions:** для `BOOK` немає доступного `BOOK_COPY` (EARS-04).
- **Postconditions:** створено `RESERVATION` зі статусом очікування; примірник блокується для інших (EARS-05).

## 4. Обґрунтування меж системи (Out of Scope)

- Система не обробляє платежі напряму: оплата штрафів делегується зовнішньому платіжному сервісу; у межах системи лише фіксується результат (`FINE.paid`) (EARS-10). Деталі платіжного потоку не зафіксовані в ADR — припущення.
- Система не веде фізичну інвентаризацію примірників і не відстежує їхнє фізичне розташування; `BOOK_COPY.status` — логічний стан.
- Система не підтримує електронні книги, міжбібліотечний обмін, фізичну логістику (`../spec.md`, розд. 8).
- Адміністративна роль поза обсягом.
- ADR 0009 — лише контекст розгортання (модульний моноліт, API-шлюз, адаптери, outbox), не обґрунтування оплати.
